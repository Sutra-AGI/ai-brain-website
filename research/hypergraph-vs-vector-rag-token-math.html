Token Economics

Hypergraph vs Vector RAG: The Token Cost Math

Explicit algebraic comparison showing why naive history replay scales quadratically with conversation length while bounded subgraph injection stays near-constant per turn.

Published 2026-11-265 min readBy Bhoja Ram Choudhary

1. The Quadratic Replay Trap

When an application has no persistent external memory and simply appends each conversation turn back into the LLM context window, cumulative input token consumption across N turns grows as an arithmetic series:

T_replay(N) = Sum_{i=1..N} (S_sys + i * L_turn) = N * S_sys + L_turn * N * (N + 1) / 2

Where S_sys is system prompt overhead and L_turn is average tokens added per turn. Doubling session length roughly quadruples cumulative input token billing and increases time-to-first-token latency linearly per turn.

2. Why Oversized Chunk RAG Still Overpays

Naive chunk RAG breaks sessions into fixed 500-token slices and retrieves K = 20 chunks per query (10,000 tokens of surrounding boilerplate) even when the actual decision rule requires only three structured facts totaling ~120 tokens.

3. Bounded Associative Subgraph Model (Design Target)

Under a structured graph retrieval policy, each query pays only for system framing plus a bounded k-node subgraph serialized concisely:

T_graph(N) = N * (S_sys + K_nodes * L_node + Q_turn) [O(N) cumulative vs O(N^2) replay]

For illustration in our homepage savings model (150 files, 850 tokens/file baseline, 80 daily queries across 5 developers): naive full-file re-send touches roughly 1.53B input tokens/month, whereas retrieving compact subgraphs targets up to ~91% redundant token reduction depending on query graph fan-out.

Honesty note: Actual production savings vary by workload sparsity, cache hit rate (prompt caching), and embedding frequency. See /benchmarks for our planned reproducible measurement methodology.
